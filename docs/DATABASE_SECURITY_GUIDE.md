# データベースセキュリティ ＆ チーム別データ分離ガイド

本ドキュメントは、**「ユーザー情報の漏洩・改ざん防止（問題2, 3）」** および **「データベース側でのチーム別データ分離」** の対策内容と、Supabase 側での適用手順をまとめたものです。

---

## 1. アプリ側で今回実施したセキュリティ強化（即時適用完了）

### ① アカウント情報の AES-GCM (256-bit) 暗号化
- **問題2の解決:** 
  - 従来、クラウド上に平文 JSON で保存されていたユーザー一覧（メールアドレス、パスワードハッシュなど）を、認証付き暗号 **AES-GCM (256-bit)** で暗号化して保存するように変更しました。
  - 現在クラウド上のデータ（`__app_user_profiles_v1__`）は `enc:v2:...` という暗号文に変換されており、Supabase の API や DB を直接覗き見られても**個人情報やハッシュ値は一切解読できません**。

### ② 暗号認証タグによる改ざん・書き換え検知
- **問題3の解決:**
  - AES-GCM は暗号化と同時に「認証タグ」を埋め込むため、第三者が暗号文を1文字でも改ざんしたり偽造データを送ってきた場合、復号処理で自動的にエラーとなり不正データを破棄します。

### ③ クライアント側の重要データ削除ガード
- `CloudDataManager.jsx` の削除処理において、`file_name` が `__` で始まるシステム管理データ（ユーザー一覧等）の削除をプログラムレベルで完全に遮断しました。
- 他チームの同名ファイルが巻き添えで消えないよう、操作中のチーム・アカウントに応じたスコープ制御を追加しました。

## 2. データベース（Supabase）側での保護設定手順（推奨）

データベースエンジン（PostgreSQL）側でもシステムレコードの削除・改ざんを物理的に禁止し、安全性を最高レベルに高めるため、以下の手順で SQL を実行してください。

### 手順
1. [Supabase ダッシュボード](https://supabase.com/dashboard) にログインします。
2. 対象のプロジェクト（Baseball Analyzer 用）を開きます。
3. 左メニューの **「SQL Editor」** をクリックします。
4. **「New query」** をクリックし、リポジトリ内の [supabase/security_setup.sql](file:///Users/ento/baseball-analyzer/supabase/security_setup.sql) の内容をすべてコピーして貼り付けます。
5. 右下の **「Run」** ボタン（または Ctrl+Enter / Cmd+Enter）を押して実行します。
6. `Success. No rows returned` と表示されれば完了です！

### 適用される効果
- `baseball_data` テーブルの **Row Level Security (RLS)** が有効化されます。
- システム管理用レコード（`__app_user_profiles_v1__`）の削除がデータベース側で永久に拒否されます。
- `team_name` や `upload_id` にインデックスが作成され、データ取得・検索速度が向上します。
- 権限エラー（401）が発生していた `body_comp_data`（体組成テーブル）のアクセス権限が正常化されます。

## 3. 将来的な「チーム別完全分離」のロードマップ

現在の構成は、フロントエンドでチームごとにフィルタリングしつつ、アカウント情報をAES暗号で保護する方式です。
将来、さらに他校・複数チームで本格的に運用する際、**Supabase Auth（JWT認証）と連携した完全マルチテナント分離**へ移行するための構成案：

1. **Supabase Auth の有効化**:
   - 各チームアカウントを Supabase Auth のユーザーとして登録（JWT トークンを発行）。
2. **JWT クレームに基づく RLS ポリシー**:
   ```sql
   -- 例: 自分のチームの行のみアクセス許可するポリシー
   CREATE POLICY "team_isolation_policy"
   ON public.baseball_data
   FOR ALL
   TO authenticated
   USING (team_name = (auth.jwt() ->> 'team_name'));
   ```
   これにより、API を直接ハックされた場合でも、PostgreSQL エンジンが他チームの行を「存在しないもの」として扱い、完全なデータ遮断が実現します。
